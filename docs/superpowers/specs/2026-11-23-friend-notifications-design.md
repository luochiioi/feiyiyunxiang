# 好友申请消息设计

沿用已确认首版设计第 7、11、15 节，以及用户在本会话确认上一段验收无问题并继续下一段开发的授权。本轮只开发好友申请消息，复用 uni-app x / UTS、uniCloud 和现有消息中心。

## 方案与范围

采用复用消息中心：新增 friend.request.received（接收人收到申请）、friend.request.accepted（申请人收到接受结果），在原好友事务内落库。相比另建收件箱，可沿用本人分页与未读；相比在消息直接操作申请，先跳转既有旅伴页处理，避免两处操作状态分叉。

实现者默认：拒绝、撤回、过期不另发通知，原消息读取时显示当前状态。不回填历史消息。固定标题和昵称快照，不公开 uid、媒体和私密资料；读消息不等于接受申请。

## 一致性与兼容

固定事件键以好友关系主键、原申请发起人及 requestId 计算；重试不重复，旧申请不能变成后来的新申请。好友消息扩展可选 friendId/friendEventKey/actorNickname 字段，既有必填 postId/revisionId/commentId/reason 保留为空字符串；不新增集合／索引。旧审核 DTO、事件键和双向已读保持不变。

通知失败必须回滚好友状态。接受相同结果重试幂等，反向决定及旧 requestId 处理新申请拒绝。旅伴页发送失败复用请求 ID，成功后读取失败只重试刷新，按账号/请求序号隔离。

## 边界

独立 worktree 从最新 main 创建，保留所有既有改动。保留澳喵、九图、审核红点/返回及步数终章等原功能；不接合作、PK、私信、注销、全站通知，不改路线/地图/剧情/AR。交付 PR，不自行合并或部署；本机、浏览器模拟、开发云、真机证据分别记录。
